# 대본과 퍼블리싱 책임의 비교

## `.github/actions/`과 `scripts/release/` 비교표

| 시나리오 | GitHub 조치 | 해당 스크립트/책임 |
|---|---|---|
| Tauri 빌드 재시도 | `.github/actions/build-tauri-with-retry/action.yml` | 재시도 구현은 Action 내부에 있으며 로컬 동등 진입점은 `scripts/rebuild.ps1`, `scripts/rebuild-linux.sh`, `scripts/rebuild-macos.sh`입니다. |
| Service 포장 | `.github/actions/stage-service-package/action.yml` | staging은 Action 내부에서 수행되며 로컬 바이너리 빌드는 `scripts/release/build-service-binaries.ps1` / `.sh`와 같은 디렉터리의 플랫폼 staging 스크립트를 사용합니다. |
| GitHub 출시 | `.github/actions/publish-github-release/action.yml` | `gh release` 업로드는 Action 내부에 구현되어 있으며 동일한 독립 로컬 스크립트는 없습니다. |
| 출시 환경 준비 | `setup-release-env` | 워크플로 내부 환경 어셈블리, 현재 완전히 동등한 독립 최상위 스크립트가 없습니다 |
| 프런트엔드 분산 준비 | `prepare-frontend-dist` | 워크플로우 내에서 프런트엔드 제품 엔드포인트 빌드/다운로드, 현재 별도의 최상위 스크립트가 없습니다 |

## 경계 합의

### `.github/actions/`

담당:

- 워크플로 내에서 재사용 가능한 단계
- 작업 전반에 걸쳐 입력과 출력을 통합합니다.
- CI/릴리스 환경 캡슐화

### `scripts/release/`

담당:

- 실제 제작, 패키징, 퍼블리싱 작업
- 로컬로 또는 워크플로별로 호출되는 스크립트 구현
- 독립적으로 실행 가능하도록 유지하십시오.

### `scripts/*.ps1|*.sh`

담당:

- 개발자를 위한 최상위 입구
- 통일된 매개변수 구성
- 복잡한 릴리스 하위 단계를 닫습니다.

## 현재 기록 스크립트 인벤토리

### 여전히 가치 있는

- `rebuild.ps1`
- `rebuild-linux.sh`
- `rebuild-macos.sh`
- `release/build-service-binaries.ps1` / `.sh`
- `release/pack-frontend-dist.sh`
- `release/publish-ghcr-images.sh`
- `release/*` 플랫폼 staging 보조 스크립트
- `ci/check-websocket-pins.sh`

이유:

- 여전히 로컬 개발, 릴리스 링크 또는 워크플로에서 실제로 사용됩니다.
- 분리된 레거시 파일이 아님

### Action 내부 구현이며 독립 스크립트가 없는 항목

`build-tauri-with-retry`, `stage-service-package`, `publish-github-release`는 `.github/actions/`에 구현되어 있으며 `scripts/release/` 아래에 같은 이름의 파일이 없습니다.

### 현재 "단일 사용 지점만 있고 직접 삭제할 수 있는" 스크립트는 발견되지 않았습니다.

이 단계에서 더 적절한 전략은 삭제가 아니라 다음과 같습니다.

1. `README.md`을 사용하여 입구 계층을 나타냅니다.
2. CI 관련 스크립트와 로컬 항목을 별도로 설명
3. 스크립트가 연속해서 여러 버전에서 참조되지 않는 경우 해당 스크립트를 보관하거나 병합하는 것을 고려하세요.

## 유지 관리 권장 사항

- 워크플로 기능을 추가할 때 기존 작업을 재사용할지 여부를 결정하는 데 우선순위를 둡니다.
- 새 릴리스 스크립트를 추가할 때 먼저 "최상위 항목"인지 "CI 하위 단계"인지 결정합니다.
- 스크립트가 로컬 실행에 적합하지 않은 경우 README에 "CI 전용"으로 명확하게 표시되어야 합니다.
