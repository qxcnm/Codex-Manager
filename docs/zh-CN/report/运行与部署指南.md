# 运行与部署指南

## 适用范围
- 桌面端首次使用
- Service 版本独立运行
- Docker 部署
- macOS 首次放行

## 快速开始
1. 启动桌面端，点击“启动服务”。
2. 进入“账号管理”，添加账号并完成授权。
3. 如回调失败，粘贴回调链接手动完成解析。
4. 刷新用量并确认账号状态。

## 通过 ccswitch 接入
如果你希望通过 ccswitch 或 Codex CLI 使用 CodexManager，可以沿用 Codex 现有的 ChatGPT 或 API Key 认证，将平台密钥只配置到 `config.toml`，无需切换登录方式：

1. 确认目标 Codex profile；使用自定义 `CODEX_HOME` 时，Codex CLI 和 CodexManager 必须指向同一个目录。
2. 进入“平台密钥”，新建一个通用 Key；如需固定 Key，可填写“自定义 API Key”，否则留空自动生成。
3. 在“Codex 接入方式”中选择“通过 CodexManager”并应用；也可通过 ccswitch 仅更新下面的 `config.toml`，将平台 Key 填入 `experimental_bearer_token`，保留现有认证设置。
4. 保存配置后重启 Codex CLI。

常见路径：
- macOS / Linux：`~/.codex/auth.json`、`~/.codex/config.toml`
- Windows：`%USERPROFILE%\.codex\auth.json`、`%USERPROFILE%\.codex\config.toml`

补充说明：

- `auth.json` 和 `config.toml` 应放在同一个 `.codex` 目录下。
- 账号直连会写入 `auth.json` 以切换到所选账号；聚合 API 直连只更新 `config.toml`，将所选聚合 API Key 写入 provider 的 `experimental_bearer_token`，保留已有 `auth.json`。
- 应用网关时，CodexManager 会逐字节保留 `auth.json`，平台 Key 只写入 `config.toml`；单纯启动软件也不会写入 `auth.json`。
- ChatGPT 与 API Key 认证（`auth_mode = "chatgpt"` 或 `"apikey"`）均可使用。应用网关不要求先运行 `codex login`，不检查 ChatGPT 登录 token，也不会因 `auth.json` 缺失而阻止配置写入；不会创建认证文件。
- 网关 provider 固定使用 `name = "cm"` 和 `requires_openai_auth = true`，不再提供移除该认证字段的开关。

示例 `config.toml`：

```toml
model = "gpt-6-sol"
model_provider = "cm"
review_model = "gpt-6-sol"
personality = "none"
model_reasoning_effort = "xhigh"
plan_mode_reasoning_effort = "xhigh"
model_reasoning_summary = "detailed"
model_verbosity = "medium"
model_supports_reasoning_summaries = true
approval_policy = "on-request"
allow_login_shell = true
sandbox_mode = "workspace-write"
cli_auth_credentials_store = "file"
chatgpt_base_url = "https://chatgpt.com/backend-api/"
mcp_oauth_credentials_store = "auto"
check_for_update_on_startup = true
web_search = "live"
approvals_reviewer = "user"
service_tier = "fast"

[model_providers.cm]
name = "cm"
base_url = "http://localhost:48760/v1"
wire_api = "responses"
requires_openai_auth = true
experimental_bearer_token = "填入你在 CodexManager 平台密钥里复制的 Key"
supports_websockets = true
```

- 如果你在设置页改过服务端口，请把 `base_url` 里的 `48760` 同步改成当前端口。
- Docker / Web 网关模式下，ccswitch / Codex CLI 应连接浏览器可访问的 Web 地址并追加 `/v1`。例如 Web UI 是 `http://10.10.121.253:48761/` 时，`base_url` 应写成 `http://10.10.121.253:48761/v1`，不要写容器内的 `localhost:48760`。
- `supports_websockets = true` 适用于通过 OpenAI 兼容协议调用 `/v1/responses` 的平台 Key。账号池路由连接官方 Codex 上游时使用原生 WebSocket；聚合 API、混合路由和非官方上游通过 CM 的 HTTP/SSE 兼容桥接接入，客户端仍使用 WebSocket，上游按已有 HTTP 路由与协议适配规则处理。桥接不会让原本不支持相应模型或协议的上游获得该能力。
- 每个桥接生成请求都经过正常网关的鉴权、模型与路由检查、并发限制及用量记录。请求日志中的 `ws` 表示客户端使用 WebSocket；桥接请求的 `method=POST` 表示内部 HTTP 请求的实际方法，不能据此判断客户端回退到了 HTTP。
- Responses 入口可适配聚合 API 的 Chat Completions action，保留文本、函数工具调用、工具结果和用量。Messages 入口直接配置 Chat Completions action 的跨协议组合不在本次支持范围内，会返回明确错误；请配置 Messages 兼容 action，或使用 Responses 入口。WS 桥接成功交付需内部 HTTP 末帧已消费且 WebSocket 终态已成功发送，真实断连仍会记录失败。
- HTTP/SSE 桥接在同一 WebSocket 连接内保留有容量限制的已完成上下文，使用 `previous_response_id` 续轮时会展开为完整 HTTP 输入。新连接、缓存超限或淘汰后无法恢复的 ID 会返回上下文恢复错误；客户端应移除该 ID 并发送完整 `input`，不要仅反复重试旧 ID。
- 桥接模式的 `generate:false` 预热在 CM 本地返回空输出和零用量，不向上游提交生成请求；真正生成时仍执行完整网关检查。
- 原生 WebSocket 会向支持 Codex 生成中断的上游透传中断控制帧。上游明确返回原因为 `interrupted` 的 `response.incomplete` 时，按正常中断记录用量并保留已完成上下文。HTTP/SSE 桥接收到中断时取消当前 HTTP 请求，返回中断确认和未完成终态，只保留已发给客户端的完成项供同连接续轮使用；关闭客户端连接也会取消当前请求。
- 桥接层不会因中断或断连自动重放已提交的生成请求。取消不能证明上游尚未处理请求或未消耗额度；已收到的用量仍由正常网关记录，真实断连及上游失败仍保留错误语义。
- 若 WS 握手返回 `426`，请核对实际 `base_url` 所连接服务的版本和平台 Key 协议。旧版服务的 `responses websocket is only available for official Codex upstream` 表示尚不支持上述兼容桥接，需要更新该服务；仅调整重连次数不会改变服务能力。

### 接入后仍显示账号，或请求日志出现 499

通过 CodexManager 接入会保留 Codex 的登录状态，因此 Codex 仍可能显示原来的 ChatGPT 账号。模型请求使用所选 provider 的 `base_url` 和平台密钥；账号显示本身不能用于判断是否绕过网关，也无需为此删除 `auth.json` 或退出登录。

先确认 Codex 与 CodexManager 使用相同的 `CODEX_HOME`，并在应用配置后重启 Codex，再对照同一时间的网关请求日志。请求已出现在 CodexManager 日志中，说明它经过了网关；日志中的上游地址表示网关选中的路由目标。

`499` 配合 `response write failed: broken pipe` 或 `downstream HTTP body closed` 表示下游客户端关闭了响应连接，可能来自主动停止、切换会话或链路断开；它不等同于 `401/403` 鉴权失败。若 Codex 同时提示错误，请保留该轮的客户端错误、时间和对应网关请求记录，以区分取消、网络问题与上游失败。截图中仅有 `499`，不足以确定客户端为什么断开。

如果 Responses HTTP 上游的成功 `response.completed` 包含完整 assistant 文本，却漏发 `response.output_item.done`，Codex 可能直接结束而不显示答案。CM 会在 completed 前为明确完成的 assistant 文本补齐缺失的 message done；已经发过 done 的消息不重复补齐，工具、图片、失败和未完成响应不补齐。每个请求新增事件累计上限为 1 MiB，消息跟踪也有数量和字节限制；超限时放弃本次补齐并保留原流。这项兼容修复不改变 `499` 表示下游真实关闭连接的含义，也不代表所有断连问题都已解决。

Responses HTTP 流在完整的响应终止事件交给 HTTP 响应体消费者后结束，CM 不再等待上游连接关闭，也不继续发送终止事件之后的保活或尾部帧。终止事件缺少完整 SSE 分隔符时会补齐，避免客户端在流结束时漏掉完成事件。这样可避免 Codex 正常结束读取时被误记为 `499`；仅解析到终止事件或把部分数据放入队列不算完成，终止事件未完整交付就断开的请求仍保留失败记录，`response.failed` / `response.incomplete` 不会被补成完整成功。因输出上限产生的未完成响应会保留可用的部分文本和用量，在 Chat / Messages 转换时标为 `length` / `max_tokens`；工具参数截断及其他无法表示的未完成状态继续保留错误。

`499` 也不表示上游没有处理请求或没有消耗额度。排查中途断开后的重试时，应统计从开始到最终成功期间的全部请求。网关请求列表每次客户端请求只显示一条最终记录；同一请求内部的上游尝试应在请求详情中另行核对。

账号的五小时额度来自官方用量接口，不是用本地请求日志的 token 数换算。未收到上游用量时，网关会按请求 JSON 字符数约四分之一估算输入 token；这个数包含请求结构开销，不能当作实际模型用量或官方扣额依据。非零缓存 token 来自上游用量，且已经包含在输入 token 中，不应重复相加。排查“多次失败后成功，但额度明显下降”时，请对齐同一账号的用量刷新时间、客户端重试记录，以及各请求的 trace ID、上游尝试次数和用量来源；仅凭最终成功记录或 `499` 数量无法确定额外消耗。

为避免重复提交，若建立上游 HTTP 响应时发生断开或响应头超时，无法确认请求是否已被处理，CM 会停止本次请求内部的自动重试、换号和备用路由，并返回可能已处理请求的错误提示。明确发生在连接建立前的失败仍可恢复，已经收到明确拒绝响应的恢复流程也保留。客户端随后自行重试属于新的请求，仍可能重新发送完整上下文；这项保护不能保证失败请求不消耗官方额度。

### 模型与路由排序

管理员可在“模型与路由”的“顺序”列拖动手柄、点击上下箭头，或聚焦手柄后按上下方向键调整模型顺序，修改会自动保存。搜索或筛选时，只重排当前显示模型的槽位，隐藏及未匹配模型的位置保持不变。多个窗口同时修改或目录发生增删时，过期的排序提交会被拒绝并重新读取目录。

模型显示顺序独立保存，不改变模型上限、价格、启用状态或路由。编辑器中的“模型等级（高级）”保留原有模型上限含义，与显示顺序分开。服务端模型列表和 CodexManager 本地模型目录沿用保存后的显示顺序；使用官方目录时，仍由官方决定模型顺序。若 Codex 使用已应用的本地目录，可再次点击“应用模型”更新所选目录。

编辑模型的“路由”页也提供拖动和箭头排序。显式移动会重新编号整个路由列表的优先级，越靠前优先级越高，点击“保存模型”后生效；未移动时保留原有优先级和同级权重。关闭编辑窗口而不保存不会提交路由顺序。

## 账号导入与导出
- `批量导入`：选择多个 `.json/.txt` 文件后统一导入。
- `按文件夹导入`：仅桌面端可用；选择目录后递归扫描其中 `.json` 文件并批量导入，空文件会自动跳过。
- `导出用户`：选择目录后按“一个账号一个 JSON 文件”导出，便于备份与迁移。

## Service 版本
1. 下载 Release 中的 `CodexManager-service-<platform>-<arch>.zip` 并解压。
2. 推荐启动 `codexmanager-start`，一个进程拉起 service + web，可直接在控制台 `Ctrl+C` 关闭。
3. 也可以只启动 `codexmanager-web`，它会自动拉起同目录的 `codexmanager-service` 并打开浏览器。
4. 或者先启动 `codexmanager-service`，再启动 `codexmanager-web`。
5. 默认地址：service `localhost:48760`，Web UI `http://localhost:48761/`。
6. 关闭：访问 `http://localhost:48761/__quit`；若 web 自动拉起过 service，会尝试一并关闭。
7. 如需自行反向代理或拆分部署前端静态资源，必须同时转发 `/api/runtime` 与 `/api/rpc`；仅托管静态文件会导致管理页面无法正常工作。

### 受控生产配置

仓库提供不含秘密的 [受控生产配置模板](../../../config/production/codexmanager.env.example) 和配套说明。复制模板后替换数据库 URL、token 文件和 provider 配置，再用 `scripts/production-acceptance.ps1` 做脱敏静态检查；脚本通过只代表配置与监听器就绪，不代表真实数据库、provider、OAuth 或反向代理验收已经完成。

### 从源码运行内嵌前端版本

源码运行时推荐使用：

```bash
./scripts/run-service-app.sh
```

脚本会先执行 `pnpm -C apps run build:desktop` 生成 `apps/out`，再编译 `codexmanager-service`、`codexmanager-web` 和 `codexmanager-start`。`codexmanager-web` 默认会把 `apps/out` 打进二进制，因此启动时不需要再手动设置 `CODEXMANAGER_WEB_ROOT`。

常用参数：

- `--debug`：使用 debug 构建，加快本地调试编译。
- `--clean-dist`：构建前清理 `apps/out`。
- `--no-open`：启动后不自动打开浏览器。

如果需要临时使用外置静态资源目录，仍可设置 `CODEXMANAGER_WEB_ROOT=/path/to/out` 覆盖内嵌资源。

## Docker 部署

Docker 镜像默认设置 `TZ=Asia/Shanghai`，compose 示例使用 `TZ=${TZ:-Asia/Shanghai}`：如果部署环境已经设置 `TZ`，会直接沿用；否则回退到 `Asia/Shanghai`。如果部署在其他地区，请设置 `TZ` 或在 compose 的 `environment` 中改成自己的 IANA 时区，例如 `Europe/London`、`America/Los_Angeles`。

### GitHub Packages / GHCR
- Release 发布后会同时推送 `codexmanager-service` 和 `codexmanager-web` 镜像到 GitHub Packages（GHCR）。
- 正式版本会同时更新版本号、`stable` 和 `latest` 标签；预发布版本只推送版本号标签，不会覆盖浮动标签。
- 自动更新建议使用 `stable`；固定版本可直接拉取对应发布 tag，例如：`docker pull ghcr.io/qxcnm/codexmanager-service:v0.6.0`。
- 仓库里的 [`docker/docker-compose.release.yml`](../../../docker/docker-compose.release.yml) 默认使用 `stable`。需要固定版本时再设置 `CODEXMANAGER_RELEASE_TAG`。
- 例如：`CODEXMANAGER_RELEASE_TAG=v0.6.0 docker compose -f docker/docker-compose.release.yml up -d`
- `registry.cn-hangzhou.aliyuncs.com/kilimiao/codex-manager` 不在当前官方发布工作流中，版本可能落后；官方维护和推荐的预构建镜像地址是上述 GHCR `service` / `web` 镜像。

### Docker OTA 更新（可选）

- 官方 Release Compose 已内置可选的 Watchtower OTA 检查 sidecar。保持 `CODEXMANAGER_RELEASE_TAG` 为默认的 `stable`（或其他会移动的浮动 tag），执行下面的命令即可启用检查：

  ```bash
  docker compose -f docker/docker-compose.release.yml --profile ota up -d
  ```

- Watchtower 每 300 秒检查一次带有更新标记的 CodexManager service / web 镜像，但 `ota` profile 只报告可用更新，不会替换容器。可通过 `CODEXMANAGER_OTA_INTERVAL=60` 调整检查间隔（单位：秒），用 `docker compose -f docker/docker-compose.release.yml logs -f codexmanager-ota` 查看结果。
- 确认升级后再执行一次下面的命令，明确同意拉取新镜像并滚动重启：

  ```bash
  docker compose -f docker/docker-compose.release.yml --profile ota run --rm --no-deps codexmanager-ota \
    --label-enable --run-once --cleanup --rolling-restart --stop-timeout 20s
  ```

- 如果用户明确同意自动检查并升级，可以使用 `ota-auto` profile：

  ```bash
  docker compose -f docker/docker-compose.release.yml --profile ota-auto up -d
  ```

- 如果设置了固定版本，例如 `CODEXMANAGER_RELEASE_TAG=v0.6.2`，OTA 不会跨版本升级；切回 `stable` 后才会跟随正式 Release。OTA sidecar 需要读取 Docker socket，因此只建议在你信任的主机上启用。
- service 重启时会继续使用同一个 `/data` 卷执行自动迁移；本次迁移路径包含迁移锁、在线备份、迁移前检查、迁移后 smoke check 和失败恢复，升级过程中不要删除该卷。

### 方式 1：all-in-one 单容器
```bash
docker compose -f docker/docker-compose.all-in-one.yml up -d --build
```

浏览器打开：`http://localhost:48761/`

- 该模式只构建一个镜像，容器内由 `codexmanager-start` 同时拉起 `codexmanager-service` 和 `codexmanager-web`。
- 默认只暴露 `48761`。Web 管理页面、`/api/rpc` 和 OpenAI 兼容网关路径（如 `/v1/responses`、`/v1/chat/completions`、`/v1/messages`）都从该端口进入；`48760` 仅在容器内部由 web 反代到 service。
- 远程服务器上使用 ccswitch 导入时，endpoint 应使用当前 Web UI 地址生成，例如 `http://10.10.121.253:48761/v1`。如果显示成 `localhost`，请先手动改为服务器地址加 `/v1`。
- 数据库、RPC token、Web 密码和运行设置都保存在同一个 `/data` 卷里。

### 方式 2：docker compose 双容器
```bash
docker compose -f docker/docker-compose.yml up --build
```

浏览器打开：`http://localhost:48761/`

### 方式 3：分别构建和运行
```bash
# service
docker build -f docker/Dockerfile.service -t codexmanager-service .
docker network create codexmanager-net

docker run --rm --name codexmanager-service \
  --network codexmanager-net \
  --network-alias codexmanager-service \
  -p 48760:48760 \
  -v codexmanager-data:/data \
  -e TZ=Asia/Shanghai \
  -e CODEXMANAGER_RPC_TOKEN=replace_with_your_token \
  codexmanager-service

# web（容器之间请走容器网络地址，不要写宿主机映射端口）
docker build -f docker/Dockerfile.web -t codexmanager-web .
docker run --rm --name codexmanager-web \
  --network codexmanager-net \
  -p 48761:48761 \
  -v codexmanager-data:/data \
  -e TZ=Asia/Shanghai \
  -e CODEXMANAGER_WEB_NO_SPAWN_SERVICE=1 \
  -e CODEXMANAGER_SERVICE_ADDR=codexmanager-service:48760 \
  -e CODEXMANAGER_RPC_TOKEN=replace_with_your_token \
  codexmanager-web
```

- 注意：若希望 Web 密码、设置项、缓存模型列表等状态与 service 保持一致，`codexmanager-web` 必须和 `codexmanager-service` 共享同一份 `/data` 卷。
- 若你坚持让容器访问宿主机映射端口，在 Linux 上还需要额外增加 `--add-host=host.docker.internal:host-gateway`；否则 `host.docker.internal` 往往无法解析。

## macOS 首次启动
- 当前 macOS Release 产物未使用 Apple Developer 账号完成公证，因此首次从浏览器下载后，Gatekeeper 可能提示“已损坏”或拒绝打开。
- Release 中的 macOS `dmg` 已内置 `Open CodexManager.command` 与 `README-macOS-first-launch.txt`。
- 推荐先把 `CodexManager.app` 拖到“应用程序”，再双击该脚本完成首次放行。
- 也可以直接执行：

```bash
xattr -dr com.apple.quarantine /Applications/CodexManager.app
```

- 如果仍被拦截，再对 `CodexManager.app` 执行一次“右键 -> 打开”。
