# 脚本与发布职责对照

## `.github/actions/` 与 `scripts/release/` 对照表

| 场景 | GitHub Action | 对应脚本/职责 |
|---|---|---|
| Tauri 构建重试 | `.github/actions/build-tauri-with-retry/action.yml` | Action 内实现重试；本地等价入口为 `scripts/rebuild.ps1`、`scripts/rebuild-linux.sh`、`scripts/rebuild-macos.sh` |
| Service 打包 | `.github/actions/stage-service-package/action.yml` | Action 内完成 staging；本地二进制由 `scripts/release/build-service-binaries.ps1` / `.sh` 构建，并使用同目录平台 staging 脚本 |
| GitHub Release 发布 | `.github/actions/publish-github-release/action.yml` | Action 内实现 `gh release` 上传；没有同名独立本地发布脚本 |
| release 环境准备 | `setup-release-env` | workflow 内环境装配，当前没有完全等价的独立顶层脚本 |
| 前端 dist 准备 | `prepare-frontend-dist` | workflow 内构建/下载前端产物收口，当前没有单独顶层脚本 |

## 边界约定

### `.github/actions/`

负责：

- workflow 内可复用步骤
- 跨 job 统一输入输出
- CI / Release 环境封装

### `scripts/release/`

负责：

- 实际构建、打包、发布动作
- 被本地或 workflow 调用的脚本实现
- 尽量保持可独立执行

### `scripts/*.ps1|*.sh`

负责：

- 面向开发者的顶层入口
- 统一参数组织
- 将复杂 release 子步骤收口

## 当前历史脚本盘点

### 仍有保留价值

- `rebuild.ps1`
- `rebuild-linux.sh`
- `rebuild-macos.sh`
- `release/build-service-binaries.ps1` / `.sh`
- `release/pack-frontend-dist.sh`
- `release/publish-ghcr-images.sh`
- `release/*` 平台 staging 辅助脚本
- `ci/check-websocket-pins.sh`

原因：

- 仍被本地开发、发布链路或 workflow 实际使用
- 不是孤立遗留文件

### Action 内实现且没有同名独立脚本

`build-tauri-with-retry`、`stage-service-package`、`publish-github-release` 的实现保留在 `.github/actions/`，`scripts/release/` 下没有同名文件。

### 当前未发现“只剩单点用途且可直接删除”的脚本

现阶段更合适的策略不是删除，而是：

1. 用 `README.md` 标明入口分层
2. 把 CI 专用脚本与本地入口分开描述
3. 后续如果某个脚本连续多个版本无人引用，再考虑归档或合并

## 维护建议

- 新增 workflow 能力时，优先判断是否应复用现有 action
- 新增发布脚本时，先决定它是“顶层入口”还是“CI 子步骤”
- 若脚本不适合本地执行，要在 README 中明确标成“仅 CI”
