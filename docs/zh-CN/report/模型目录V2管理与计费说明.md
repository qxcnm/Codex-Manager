# 模型目录 V2 管理与计费说明

本文说明当前模型目录、路由、instructions policy、Codex 目录应用、价格同步和钱包计费的实际行为。模型目录 V2 已一次性接管运行时；旧模型来源、旧价格规则和供应商模型发现表只为迁移审计保留，不再参与请求。

## 1. 唯一真相源

- 模型来源只有 `builtin` 和 `custom`。
- fresh DB 会写入 12 个 builtin 行：`gpt-6.1-sol`、`gpt-6-astra`、`gpt-6-sol`、`gpt-6-luna`、`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5`、`gpt-image-2`、`gpt-image-2.5-sunburst` 和 `gpt-image-2.5-flare` 共 11 个模型为 enabled、`supported_in_api=true`、`visibility=list`，只有 `codex-auto-review` 为 `visibility=hide`。
- `gpt-5.4` 与 `gpt-5.4-mini` 已于 2026-08-31 从 ChatGPT 登录的 Codex 退役，`gpt-5.2` 也已在该登录方式下 deprecated，因此 revision 9 不再把三者写入 fresh builtin 目录。通用 API 模型不受此清理影响；需要继续使用对应 slug 时，可保留或显式新增 custom 模型与 route。
- 本地 `/v1/models` 只读取 enabled、`visibility=list`、`supportedInApi=true` 的 V2 数据，不联网、不补建记录、不写数据库。
- 启动、模型页、账号切换、聚合 API 页面和 Gateway 都不会自动请求上游或供应商 `/models`；管理员可在聚合 API 列表或账号页的明确账号上主动拉取并选择性关联模型。
- 其他模型通过“新增自定义模型”手工添加，或从本地 JSON 导入。

`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 的每 1M tokens 基础 input/cached input/cache write/output 费率分别为 `5/0.5/6.25/30`、`2/0.2/2.5/12`、`0.2/0.02/0.25/1.2` USD，状态标为 `official`。输入超过 272000 tokens 时，三款模型分别切换到 `10/1/12.5/45`、`4/0.4/5/18`、`0.4/0.04/0.5/1.8` 的长上下文费率；hidden 的 `codex-auto-review` 仍明确显示 `price missing`，不是零价。

`gpt-6.1-sol` 是 revision 10 新增的可见 builtin（2026-09-30 核对 [官方模型卡](https://developers.openai.com/api/docs/models/gpt-6.1-sol) 与 [官方价格页](https://developers.openai.com/api/docs/pricing)）。它面向复杂编程、计算机操作和专业工作，以较低成本提供接近 Astra 的能力。Standard 每 1M tokens 的 input/cached input/cache write/output 价格为 `2/0.1/2.5/10` USD；总输入超过 272000 tokens 后整次请求使用 `4/0.2/5/15` USD。API 上下文为 1050000、最大输出为 128000；Codex 目录沿用现有 GPT-6 的 272000/872000 工作上下文预算。推理档位为 `low/medium/high/xhigh/max`，默认 `medium`，不支持 `none/minimal`；工具调用须使用 Responses，原生 Chat Completions 仅支持无工具请求。支持文本和图片输入、文本输出及流式输出，目录声明 Fast（`priority`），不声明 Ultrafast。这里内置的是 Standard 价格，Fast/Batch/Flex 等账单不能仅由该基价推导为实际费用。SQLite 与 SeaORM 后端均补种该模型，保留已有模型、同名 custom、用户编辑价格/路由和删除墓碑；目录存在不代表账号已经获得上游访问权限。

`gpt-6-sol` 和 `gpt-6-luna` 是当前可见的 GPT-6 builtin。两者每 1M tokens 的基础 input/cached input/cache write/output 费率分别为 `2/0.2/2.5/10` 与 `0.1/0.01/0.125/0.5` USD；输入超过 272000 tokens 后分别切换到 `4/0.4/5/15` 与 `0.2/0.02/0.25/0.75` 的长上下文费率。两者均声明 Fast（`priority`）service tier，并保留独立的 Codex runtime 元数据。

`gpt-6-astra` 是 revision 8 新增的可见 builtin。OpenAI 公开 API 限制为 1050000 context window、922000 max input tokens 和 128000 max output tokens；目录同时保留 Codex 客户端使用的 272000 context window 与 872000 max context window 运行元数据。其每 1M tokens 官方 input/cached input/cache write/output 基础费率为 10/1/12.5/50 USD；输入超过 272000 tokens 后切换为 20/2/25/75 USD。公开 API 的 reasoning effort 支持 `low`、`medium`、`high`、`xhigh`、`max`；目录中的 `ultra` 是 Codex 客户端在 `max` 之上的编排元数据，并不是发送给 API 的 reasoning value。服务等级只声明 `priority`（界面显示 Fast），不声明 Ultrafast。

`gpt-image-2`（快照 `gpt-image-2-2026-04-21`）、`gpt-image-2.5-sunburst`（快照 `gpt-image-2.5-sunburst-2026-09-08`）和 `gpt-image-2.5-flare`（快照 `gpt-image-2.5-flare-2026-09-08`）是当前图片 builtin。三者的 capability 只声明文本/图片输入、图片输出、图片生成与编辑，以及 `/v1/images/generations`、`/v1/images/edits` 两个直接端点；不声明文本生成，也不能把这些 slug 直接当作 `/v1/responses` 或 `/v1/chat/completions` 的主模型。Image 2.5 的官方输入价格按 text/image 模态分别计价，而当前 V2 快照只有统一 input/cached input 桶，因此这两个模型保留官方价格来源但标记为 `price missing`、不创建统一价 tier，仍可列出和配置 route，但不会自动计费。Responses 中由主模型调用 `image_generation` 内置工具属于另一条接口链路，不能据此放宽这些目录项的用途边界。

Images API 兼容入口的主对话模型默认使用 `gpt-6-luna`，注入的图片工具模型默认仍为 `gpt-image-2`；两个 Image 2.5 模型可通过模型目录或环境变量显式选择。

free-account 模型上限选项只从当前可用于文本生成的模型目录生成。已持久化但不再属于当前候选目录、图片专用或旧 fallback 的 ceiling 值会归一化为 `auto`，不会把失效 slug 重新加入候选；该设置仍只过滤 Free 账号候选，不改写请求中的模型。

## 2. 模型管理页

列表同时展示：

- origin：`builtin` / `custom`
- enabled 与 visibility
- price status：`official` / `estimated` / `custom` / `missing`
- instructions mode：`passthrough` / `fallback` / `override`
- enabled route 数量或 `missing route`

统计卡片显示 total、enabled、builtin、custom、price missing 和 missing route。hidden 模型不会混入默认列表，选择 hidden 筛选后才会出现。

管理员操作区提供两个明确动作：

- “应用模型”在未勾选时把完整目录写入 Codex 配置；存在勾选项时只写入所选模型。写入后需要关闭并重新打开 Codex。
- “同步价格”从外部价格元数据更新可匹配模型的价格。同步不会在页面打开、服务启动或普通目录读写时自动执行。

删除语义：

- builtin 只能禁用，记录、价格和审计信息不会被物理删除。
- custom 可以物理删除。
- 删除聚合 API 连接时，会删除引用该连接的 V2 routes；不会反写 legacy 模型表。

## 3. 一次原子保存

模型编辑器分为四区，点击一次“保存模型”只调用一次 V2 upsert RPC，并由一个数据库事务保存：

1. 基本信息和关键 capabilities。
2. input、cached input、output 三价，以及可选 long-context tier。
3. `account_pool` / `aggregate_api` routes；上游模型名手工填写。
4. instructions mode 和可选文本。

对支持推理的自定义模型，可在基本信息中选择实际支持的强度档位，并可从已选档位中指定默认值，也可保持“不指定”。未选档位表示模型不声明推理能力；聚合 API 连接或拉取模型时不会替上游猜测支持范围。档位和默认值分别保存在 V2 模型的 `capabilities.reasoningEfforts` 与 `defaultReasoningEffort`，生成的 Codex 目录会写出 `supported_reasoning_levels` 与 `default_reasoning_level`。例如已验证支持 `low`、`medium`、`high` 的聚合模型，可以仅勾选这三档并把 `medium` 设为默认。具体可用档位以该上游实际能力为准。

同一事务还会保存 permission group 关联。任一步校验或写入失败，整次保存回滚，不会出现“模型保存成功但价格或 route 保存失败”的半状态。

价格 UI 使用 USD / 1M tokens；提交时从十进制字符串无损转换为整数 micro-USD。最多支持 6 位有效小数，禁止负数、非数字、部分三价和超出 JavaScript 安全整数范围的值。

长上下文 tier 的 `minInputTokens` 是包含 cached tokens 的总 input token 阈值。系统选择不大于实际 input tokens 的最高档；`gpt-5.5` 从 272000 tokens 起切换，三款 GPT-5.6 模型、`gpt-6.1-sol`、`gpt-6-astra`、`gpt-6-sol` 和 `gpt-6-luna` 从 272001 tokens 起切换。

### 管理员手动同步价格

管理员点击“同步价格”后，服务同时读取两个公开来源：

1. `basellm` 的 `https://basellm.github.io/llm-metadata/api/all.json` 是主来源。
2. `models.dev` 的 `https://models.dev/api.json` 用于补全主来源没有的数据，并在主来源不可用时回退。

任一来源失败时，只要另一个来源成功，服务仍会完成匹配和更新，并在结果中标记失败来源；两个来源都失败时，本次同步报错且不写价格。同步结果会汇总 updated、unchanged、preserved custom、unmatched 和 ambiguous 数量。

外部同步写入的价格状态统一为 `estimated`。未勾选模型时，`price_status=custom` 的基础价格和 price tiers 全部保留，不会被外部数据覆盖；明确勾选的模型则允许外部价格覆盖已有自定义价格。持久化使用价格专用更新路径，通常只更新匹配模型的价格与 tiers，不会修改模型基本字段、capabilities、visibility、routes 或 `user_edited`。唯一例外是：两个来源都健康且返回了非空模型目录，并共同确认某个由本功能写入的 external `estimated` 价格已撤销或失效时，服务会在同一事务中把该价格置为 `missing`、清空 tiers，并把模型移出所有显式 permission groups，防止继续按旧价格计费；任一来源失败或返回空目录时都不会执行这项失效清理，未被明确选择的 `price_status=custom` 也不会执行失效清理。

价格同步会沿用模型管理页的勾选状态：未勾选模型时同步整个目录并保护自定义价格，勾选一个或多个模型时只同步对应 slug，并允许这些明确选中的模型覆盖自定义价格。选中的模型不存在时请求会被拒绝且不会写入任何价格；模型来源为 `custom` 不等于价格一定是自定义价格，只有未明确选择的 `price_status=custom` 才会触发价格保护。

## 4. 路由与聚合 API

每条 V2 route 包含：

- `sourceKind`：`account_pool` 或 `aggregate_api`
- `sourceId`：账号池使用 `default`，聚合来源使用连接 ID
- `upstreamModel`
- enabled、priority、weight

builtin 默认拥有 `account_pool/default` route，上游模型等于平台 slug。aggregate route 只能由用户在模型编辑器中明确保存。

聚合 API 页面只管理连接、启停、密钥、余额和 route 连通性测试。管理员主动拉取时，模型列表仅用于本次选择，不写旧供应商模型表；关联会在一个事务中创建缺失的 custom V2 模型并新增 route，已有模型只新增 route。

账号页的“获取账号模型”也只在管理员点击某个明确账号后执行：请求固定使用该账号的凭据、ChatGPT 账号标识和代理访问官方 Codex `/v1/models`，不会在账号池中轮转。拉取结果仅供本次选择；关联会创建或复用 V2 模型，并写入 `account_pool/default` route。该 route 表示账号池能力，不会持久化为只绑定本次拉取账号的专属 route。

Gateway 收到平台 slug 后按以下顺序处理：

1. 读取 enabled V2 model，并检查 `supportedInApi`、权限组和计费条件。
2. 只读 enabled V2 routes，构造账号池和聚合 API 候选。
3. 为每个候选从不可变客户端 body 独立生成请求体，避免不同 provider 候选互相污染。
4. 将 route 的 `upstreamModel` 写入该候选请求。

所有 `gpt-image-*` builtin 的目录 capability 与本地请求校验都把客户端用途限制在 Images API 兼容入口，route 本身不承担端点隔离。Images 适配器可以在内部转换为 Responses 主模型加 `image_generation` 工具；但客户端的普通 Chat Completions 或直接 Responses 请求即使显式填写图片 slug，也不应绕过端点校验进入文本生成链路。

## 5. Instructions policy

| mode | 行为 |
| --- | --- |
| `passthrough` | 客户端已有 instructions/system/developer 内容时原样保留；模型文本不参与请求。 |
| `fallback` | 任一客户端 instruction channel 非空时原样保留；全部为空时才使用模型文本。 |
| `override` | 使用非空模型文本替换顶层和连续 leading system/developer instructions。 |

builtin 默认是 `passthrough`，且 `instructions_text` 为空。seed 和生成的 `gateway-models.json` 都不携带官方人格 prompt。

真实 Codex target 最终仍执行 transport 级中性兜底：当最终 instructions 为 missing、null、空串或纯空白时，发送 `Follow the user's instructions.`。该文本不写入模型目录；非 Codex target 不接收此兜底。客户端非空内容保持原字符串，不 trim。

## 6. 本地 JSON 导入

“从本地 JSON 导入”支持：

- 模型目录 V2 导出结构。
- Codex catalog 的 `models` 结构。

流程固定为 preview 后 commit。preview 显示新增、更新、冲突、跳过、错误和忽略字段；冲突策略只有：

- `keep_existing`
- `replace_custom`

所有导入项都作为 custom 处理，不能覆盖 builtin。`base_instructions`、`instructions_template`、instructions variables 和未知 prompt 字段会被忽略；导入不联网。

## 7. 应用模型到 Codex

模型管理页不写入或下载 `~/.codex/models_cache.json`。管理员可以直接点击“应用模型”：未勾选时应用完整目录，勾选一个或多个模型时只应用所选模型。该操作不依赖平台密钥，也不会改写现有 `auth.json`、`model_provider` 或网关地址。

应用流程如下：

1. 未勾选时读取模型目录 V2 的全部记录；有勾选项时按 slug 精确读取所选记录，并生成 `gateway-models.json`。应用过程不按 enabled、`supportedInApi`、visibility、模型类别或文本生成能力过滤，因此 `gpt-image-2`、两个 Image 2.5 slug 和明确勾选的隐藏模型都可以写入；导出副本会设为可见，不修改数据库中的原始 visibility。
2. 将文件写入 CodexManager 数据目录中与目标 `CODEX_HOME` 绑定的托管 profile 目录。
3. 更新目标 `CODEX_HOME/config.toml`，使 `model_catalog_json` 指向该 `gateway-models.json`。
4. 不终止或强制重载运行中的 Codex app-server。关闭并重新打开 Codex 后读取新目录。

首次使用仍需明确执行“应用模型”。之后保存或删除模型会尽力同步当前已启用的托管网关 profile 中的目录文件，不会强制重载正在运行的 Codex 进程；重新打开 Codex 后读取新目录。`gateway-models.json` 的生成会保留推理等级和 Codex 运行元数据：GPT-5.6 Sol、Terra 包含 `low` 到 `ultra` 以及 `multi_agent_version=v2`；Luna 包含到 `max` 且为 `multi_agent_version=v1`。目录还包含 `tool_mode`、`use_responses_lite`、`max_context_window`、`comp_hash`、verbosity、apply patch、truncation 和 speed tier 等非提示词字段，不输出 `model_messages`，也不会启用 `include_skills_usage_instructions`。

服务等级按模型目录能力对 Codex 客户端暴露：`priority` 显示为 Fast，`ultrafast` 显示为 Ultrafast；当前 Astra 只有 Fast，Sol 同时声明 Fast 与 Ultrafast。平台 API Key 还接受 Standard 和兼容用的 Flex：Standard 在 Codex 上游省略 wire 字段但日志记为 `standard`，Fast 映射为 `priority`，Ultrafast 与 Flex 按原值透传，最终是否可用仍取决于模型和上游。

Max 与 Ultra 不是独立模型。Max 是所选模型的单代理最大推理强度；Ultra 由 Codex 客户端在 Max 推理强度之上主动编排子代理。兼容客户端如果直接向 Gateway 提交 `ultra`，请求日志分别保存 `client_reasoning_effort=ultra` 和最终 `reasoning_effort=max`，列表显示为 `ultra→max`。未修改的官方 Codex 会在到达 Gateway 前把 Ultra 的单次上游请求归一化为 Max，因此 Gateway 不能仅凭请求体可靠反推用户是否选择了 Ultra；`x-openai-subagent`、父线程和 turn metadata 仍会原样透传，但不会被错误推断为 Ultra。

## 8. 整数计费与快照

计费只使用 V2 DB 中实际命中的价格 tier：

```text
uncached_input = max(input_tokens - cached_input_tokens, 0)

numerator =
    uncached_input * input_rate
  + cached_input_tokens * cached_rate
  + output_tokens * output_rate

charged_cost_microusd =
  ceil(numerator * multiplier_millis / 1_000_000_000)
```

`gpt-image-2` 继续使用当前统一价元数据；两个 Image 2.5 builtin 因官方 text/image input 与 cached input 价格不同，而现有 usage 和快照不能完整保存分模态桶，所以保持 `price_status=missing` 且没有 price tiers。它们仍可用于非钱包路由；钱包计费会明确返回 `model_price_missing`，不会把全部 input tokens 按 image input 单价估算或扣费。

中间值使用 `i128`，倍率应用后只做一次最终向上取整。实际 usage 优先；缺 usage 或流式中断时使用确定性本地估算并标记 `estimated`，不会默认为 0。

价格读取、request charge snapshot、幂等 wallet ledger 和余额更新在一个 Core 事务中完成。快照保存实际 tier/rates、tokens、usage source、倍率、base cost 和 charged cost；请求 ID / request log ID 用作幂等键。后续修改价格不会改变历史快照和钱包流水。

`price_status=missing` 的模型可以在非钱包模式使用，也可以继续编辑和配置 route；它不能加入钱包扣费权限组。钱包请求会返回 `model_price_missing`，不会按零价放行，也不会 fallback 到编译期价格。

## 9. 迁移行为

首次 V2 cutover 会在维护态下排空在途 Gateway 流量和钱包写入，获取数据库旁跨进程锁，并使用 SQLite online backup 执行 preflight、单事务迁移和 smoke test。失败时在恢复流量前还原 backup。

legacy DB 的迁移规则：

- builtin fixture revision 5 新增 `gpt-image-2`。既有 revision 4 目录缺少该 slug 时只补建这个 builtin 及其默认账号池 route；若同名 slug 已由用户作为 custom 管理，则保留 custom，不强制改写为 builtin。
- builtin fixture revision 8 新增 `gpt-6-astra`，并补齐未编辑 `gpt-5.6-sol` 的 Ultrafast 能力。升级目录只补建缺失的 Astra 及默认账号池 route；若同名 slug 已由用户作为 custom 管理，或 builtin 已由用户编辑，则保留用户数据。

## 10. 常见排查

### 模型不在普通列表

检查 enabled、visibility 和 `supportedInApi`。hidden 模型只在 hidden 筛选中出现；本地 `/v1/models` 也不会列出 hidden。

### 模型显示 missing route

在模型编辑器的“路由”页签添加 enabled route，并确认 aggregate route 的 source ID 对应仍存在且 active 的聚合 API。

### 钱包请求返回 `model_price_missing`

补齐 input/cached/output 三价后保存，或不要把该模型加入钱包扣费权限组。不要把空价格填写为 0 来绕过校验。

### 聚合 API 连通性测试提示没有 route

先在模型目录 V2 中为该连接保存一条 enabled aggregate route，或在聚合 API 页面主动拉取并关联上游模型。聚合 API 页面不会后台自动发现上游模型。

### Codex `/model` 没有立即更新

在模型管理页点击“应用模型”；未勾选时会应用完整目录，存在勾选项时只应用所选模型。该操作会重新生成 `gateway-models.json`，只更新 `config.toml` 的 `model_catalog_json`，不会终止运行中的 Codex 后台进程。关闭并重新打开 Codex 后会显示新列表。
