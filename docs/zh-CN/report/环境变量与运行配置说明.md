# 环境变量与运行配置说明

## 目标

本文档用于集中说明 CodexManager 的环境变量加载规则、设置页持久化规则，以及常用配置项的推荐改法。

源码中的 `CODEXMANAGER_*` 常量仍是最终准入标准；本文档负责给协作者提供稳定入口，不替代源码校验。

## 配置来源与优先级

当前配置来源主要有四层：

1. 系统环境变量 / 启动命令环境变量
2. 可执行文件同目录环境文件：`codexmanager.env` -> `CodexManager.env` -> `.env`
3. `app_settings` 持久化表
4. 桌面端设置页的专属设置卡片 / 高级环境变量编辑器

实际生效优先级可概括为：

- 当前进程已存在环境变量（包括启动前系统环境变量，以及启动时从 `env` 文件读入的值）
- 专属设置卡片 / 持久化 `envOverrides`
- 代码默认值

补充规则：

- 环境文件只会注入“当前进程尚未定义”的变量
- 进程启动后，设置页保存的 `envOverrides` 只会补齐“当前进程还没有”的变量
- 桌面端当前已改为 `env` 优先：如果进程里已经有同名 `CODEXMANAGER_*` 变量，设置页持久化配置不会再覆盖它
- 支持热更新的 service 运行时配置会立即 reload，但同名 `env` 已存在时会优先沿用 `env`
- bootstrap 级变量仍要求在进程启动前准备好

## env 文件放哪

当前进程会按下面顺序在“可执行文件同目录”查找环境文件：

- `codexmanager.env`
- `CodexManager.env`
- `.env`

也就是说：

- 启动桌面端程序时，`env` 文件要放在桌面端实际可执行文件所在目录
- 启动 `codexmanager-start` / `codexmanager-service` / `codexmanager-web` 时，`env` 文件也要放在对应可执行文件旁边
- 三种文件名只会命中一个，优先推荐统一使用 `codexmanager.env`

## 常用变量分组

### 账户模型资格缓存

- `CODEXMANAGER_ACCOUNT_MODEL_UNSUPPORTED_TTL_SECS`：账户与最终发送模型的资格拒绝缓存有效期，默认 `1800` 秒。未设置、`0`、负数或非法值均回退默认值。支持通过高级环境变量设置；更新只影响之后写入的拒绝记录，已有记录沿用写入时的有效期。该缓存只在当前 service 进程内生效，桌面端内置 service 与独立 service 各自维护；重启后清空，不写入数据库。仅完整的明确模型资格错误会写入，工具模型与参数错误不会影响主模型；已确认完成的成功响应会清除对应账户与模型记录。

### 地址与入口

- `CODEXMANAGER_SERVICE_ADDR`：service 地址，默认 `localhost:48760`
- `CODEXMANAGER_WEB_ADDR`：web 地址，默认 `localhost:48761`
- `CODEXMANAGER_WEB_ROOT`：web 静态资源目录
- `CODEXMANAGER_LOGIN_ADDR`：本地 OAuth 回调监听地址

### Docker 容器

- `TZ`：容器时区，Docker 镜像默认 `Asia/Shanghai`；compose 示例使用 `${TZ:-Asia/Shanghai}`，会优先沿用部署环境里的 `TZ`，没有设置时回退到 `Asia/Shanghai`。其他地区部署时请改成自己的 IANA 时区。

### 网关与上游

- `CODEXMANAGER_UPSTREAM_BASE_URL`
- `CODEXMANAGER_UPSTREAM_PROXY_URL`
- `CODEXMANAGER_UPSTREAM_PROXY_BYPASS_HOSTS`
- `CODEXMANAGER_UPSTREAM_TOTAL_TIMEOUT_MS`：网关请求总超时，单位毫秒；默认 `0`，表示服务端不主动按总时长截断请求。
- `CODEXMANAGER_UPSTREAM_STREAM_TIMEOUT_MS`
- `CODEXMANAGER_HTTP_TIMEOUT_MS`：Service Axum 前置入口对普通（非 SSE / WebSocket）HTTP 请求的总超时，单位毫秒；默认 `120000`（120 秒），设置为 `0` 可关闭该层超时。流式响应和 WebSocket 始终沿用各自的网关超时语义。
- `CODEXMANAGER_GATEWAY_ASYNC_STREAM_WORKERS`：异步上游任务并发上限；默认 `32`，最大 `256`。许可持续到响应体结束或取消，并在通道满时传播背压，不会为每条流创建线程。
- `CODEXMANAGER_FRONT_PROXY_MAX_BODY_BYTES`：前置代理通用请求体上限，单位字节；默认 `0` 表示不设置通用上限，但 zstd 请求仍受独立的解压安全上限保护。
- `CODEXMANAGER_REQUEST_LOG_PAYLOAD_QUEUE_MAX_BYTES`：请求内容日志写入队列的内存预算，按所有已入队、尚未落库的请求体总字节计算；支持 `134217728`、`128MiB`、`1GiB` 等写法。默认按 `min(物理内存, 容器 cgroup 内存限制) / 32` 计算并限制在 32 MiB～1 GiB。超出预算的请求内容按顺序写入数据库所在目录下的 `request-log-spill/` 后再补写入库；磁盘空间不足时丢弃并在日志页提示。日志记录不会阻塞请求的接收与转发，启动日志 `event=request_log_payload_queue_budget` 会输出最终预算与依据。
- `CODEXMANAGER_FRONT_PROXY_ZSTD_MAX_BODY_BYTES`：zstd 请求解压后的安全上限，单位字节；默认 `268435456`（256 MiB）。声明了 zstd 编码时，压缩体读取也使用该上限；显式通用上限不为 `0` 时两者取较小值。该项必须大于 `0`，填 `0` 或非法值会回退安全默认值。可在设置页“环境变量”中保存并立即作用于后续请求。
- `CODEXMANAGER_MAX_TEXT_INPUT_CHARS`：网关本地文本输入上限，默认 `1048576` 个 Unicode 字符；`0`、负数或非法值会回退默认值。统计 `/v1/responses` 的 `input`、`/v1/chat/completions` 与 `/v1/messages` 的消息正文，以及 `instructions`。可在设置页“环境变量”中保存并立即作用于后续请求；桌面端和 service 模式都由同一网关执行。长对话或压缩请求可按需要调高，例如 `2097152`；该项独立于请求体字节上限，也不会提高上游模型的 token 或上下文上限。
- `CODEXMANAGER_USE_WEBSOCKET_UPSTREAM`：是否让 ChatGPT `/v1/responses` 流式上游优先尝试 WebSocket 传输；默认 `0`。这是实验开关，失败会回退 HTTP 流式路径，会沿用上游代理与连接超时配置。启用后，单个账号/上游目标的 WebSocket 流在没有完整收到 `response.completed` 时会进入 30 秒冷却；冷却期间后续请求直接走 HTTP，冷却结束只允许一个 WebSocket 探测，只有探测完整收到 `response.completed` 才清除冷却。该机制只控制 Manager 到上游的传输，不会强制已经回退到 HTTP 的 Codex session 重新升级为下游 WebSocket。
- `CODEXMANAGER_SSE_KEEPALIVE_ENABLED`：是否向下游 SSE 发送注释心跳，默认 `1`；设为 `0` 会禁用心跳，但保留已配置的间隔。它只作用于流式 SSE；非流式 Images JSON 响应仍需依赖足够长的客户端和反向代理读取超时。
- `CODEXMANAGER_SSE_KEEPALIVE_INTERVAL_MS`
- `CODEXMANAGER_PROXY_LIST`
- `CODEXMANAGER_ROUTE_STRATEGY`

### Codex 图片生成

- `CODEXMANAGER_CODEX_IMAGE_GENERATION_ENABLED`：是否启用图片生成兼容链路，默认 `1`。
- `CODEXMANAGER_CODEX_IMAGE_MAIN_MODEL`：Images API 兼容入口内部使用的主对话模型，默认 `gpt-6-luna`。
- `CODEXMANAGER_CODEX_IMAGE_TOOL_MODEL`：图片工具模型，默认 `gpt-image-2`。

补充说明：

- `/v1/images/generations` 与 `/v1/images/edits` 会转换为内部 `/v1/responses + image_generation tool` 链路。
- Codex CLI 原生传入 `tools[].type = "image_generation"` 时会保持透传，不会影响既有文本请求链路。

## Service 数据库切换与离线导入

Service SeaORM 数据库通过 `CODEXMANAGER_STORAGE_BACKEND`（`sqlite`、`mysql` 或 `postgres`）和
`CODEXMANAGER_DATABASE_URL` 配置；`CODEXMANAGER_DB_MAX_CONNECTIONS`（默认 `10`）和
`CODEXMANAGER_DB_ACQUIRE_TIMEOUT_MS`（默认 `5000`）控制 SeaORM 连接池。
`CODEXMANAGER_STORAGE_MAX_CONNECTIONS` 等 `STORAGE_*` 参数控制兼容 `Storage` 句柄池，
不替代 SeaORM 参数。远端配置不完整或后端不匹配会在启动前失败，不会回退到本地 SQLite。

显式设置 `CODEXMANAGER_DATABASE_URL` 即选择 SeaORM，包括 `sqlite` 后端；空 URL 也会
报配置错误。SQLite URL 示例为 `sqlite://C:/data/service.sqlite?mode=rwc`。未设置 URL
且后端为默认 `sqlite` 时，保留桌面 `CODEXMANAGER_DB_PATH` 与原迁移流程。选择 SeaORM
后，业务数据只从指定 URL 读取和写入，`CODEXMANAGER_DB_PATH` 不再是业务数据源。

Service 默认构建只带 SQLite 驱动。MySQL 构建使用
`cargo build -p codexmanager-service --release --no-default-features --features storage-mysql`；
PostgreSQL 使用 `--features storage-postgres`。现有未带对应 feature 的二进制不会因
设置环境变量自动获得驱动。

`codexmanager-web` 和 `codexmanager-start` 启动时也会读取数据库设置，必须编译相同驱动：
`cargo build -p codexmanager-service -p codexmanager-web -p codexmanager-start --release --features storage-mysql`
（PostgreSQL 改为 `storage-postgres`）。三个包均转发 `storage-sqlite`、`storage-mysql`、
`storage-postgres` feature；默认发行行为仍是 SQLite。只编译 Service 驱动不能让另外两个
单独构建的二进制获得远端数据库能力。

`cargo run -p codexmanager-storage-seaorm --bin storage-transfer -- export SOURCE.sqlite SNAPSHOT.jsonl`
导出只读、带校验和的快照；`inspect` 只检查快照；`import` 从
`CODEXMANAGER_STORAGE_BACKEND` 和 `CODEXMANAGER_DATABASE_URL` 读取目标，并要求目标为空。
未知有数据表、未映射列、校验和不一致或目标非空都会整笔回滚。快照含认证凭据，必须按
敏感备份管理，命令不会把凭据写入诊断输出。

切换顺序：停止源库写入，导出快照，执行 `inspect SNAPSHOT.jsonl`，将目标 URL 留在
环境配置中，再运行 `cargo run -p codexmanager-storage-seaorm --features mysql --bin storage-transfer -- import SNAPSHOT.jsonl`
（PostgreSQL 改用 `--features postgres`）。确认导入报告后，用相同目标配置启动对应
Service 二进制，并验收认证、授权、读写和网关。源 SQLite 保留，导入工具不会修改它；
目标非空时禁止重复导入。运行中不能改 URL 热切换，必须停止服务后重新启动。

### 后台任务与并发

- `CODEXMANAGER_USAGE_POLLING_ENABLED`
- `CODEXMANAGER_USAGE_POLL_INTERVAL_SECS`
- `CODEXMANAGER_GATEWAY_KEEPALIVE_ENABLED`

- `CODEXMANAGER_TOKEN_REFRESH_POLLING_ENABLED`
- `CODEXMANAGER_TOKEN_REFRESH_POLL_INTERVAL_SECS`
- `CODEXMANAGER_WARMUP_CRON_ENABLED`
- `CODEXMANAGER_WARMUP_CRON_EXPRESSION`
- `CODEXMANAGER_USAGE_REFRESH_WORKERS`
- `CODEXMANAGER_FRONT_PROXY_WORKER_THREADS`：进程级主 Tokio runtime 的执行线程数，默认 `2`，最小 `1`；Service/Web/Tauri IPC、后台认证及数据库共用。
- `CODEXMANAGER_FRONT_PROXY_MAX_BLOCKING_THREADS`：主 runtime 的文件/SQLite/CPU blocking 线程上限，默认跟随存储连接池上限且不超过 `32`。

上述两个线程参数在进程首次初始化主 runtime 时生效，修改后需重启进程。同进程
listener 停止或重启会关闭监听端口并等待响应记账完成，但共享 runtime 保持运行，
以保留后台登录及复用 HTTP 连接所依赖的连接驱动。

同步 RPC、Rhai 和插件调度的兼容 worker 为固定 8 个线程，最多接纳 40 个运行/排队任务，
与 Tokio blocking pool 分开，防止同步 ABI 等待自身异步文件/数据库阶段时耗尽同一池。
原生网络 handler 直接 await；保留的同步桥最多 32 个同时等待。设备码登录最多 64 个并发任务。
停服会等待 OAuth listener、设备码登录取消与状态写回、插件 scheduler、已接纳兼容任务
及网关记账，随后同进程可以重新启动。

`CODEXMANAGER_HTTP_WORKER_FACTOR`、`CODEXMANAGER_HTTP_WORKER_MIN`、
`CODEXMANAGER_HTTP_STREAM_WORKER_FACTOR`、`CODEXMANAGER_HTTP_STREAM_WORKER_MIN`
只保留旧设置的读写兼容，不再调整生产 Axum listener；使用这些参数的旧 HTTP worker
仅存在于测试夹具中。当前生产网关同时准入最多 `32` 个路由任务，并在联系 provider
前预留最多 `256` 个响应生命周期名额；普通 RPC 阻塞处理上限为 `32`，原生异步 RPC
上限为 `64`。这些上限不是 Tokio 线程数，异步上游响应任务另受
`CODEXMANAGER_GATEWAY_ASYNC_STREAM_WORKERS` 限制。

### 存储与鉴权

- `CODEXMANAGER_DB_PATH`
- `CODEXMANAGER_RPC_TOKEN`
- `CODEXMANAGER_RPC_TOKEN_FILE`
- `CODEXMANAGER_NO_SERVICE`
- `CODEXMANAGER_STORAGE_MAX_CONNECTIONS`：旧 `Storage` 句柄池每个数据库路径的句柄上限，默认 `32`。默认 SQLite 模式使用业务库句柄；SeaORM 模式使用同一套池管理无 schema 的兼容内存句柄，不会因此打开本地业务库。

## 文件夹示例

### 桌面端

Windows 桌面端最直观的放法如下：

```text
CodexManager/
├─ CodexManager.exe
├─ codexmanager.env
└─ 其他运行库文件...
```

对应 `codexmanager.env` 示例：

```dotenv
CODEXMANAGER_SERVICE_ADDR=localhost:48760
CODEXMANAGER_UPSTREAM_PROXY_URL=http://127.0.0.1:7890
CODEXMANAGER_UPSTREAM_TOTAL_TIMEOUT_MS=0
CODEXMANAGER_UPSTREAM_STREAM_TIMEOUT_MS=600000
CODEXMANAGER_SSE_KEEPALIVE_ENABLED=1
CODEXMANAGER_SSE_KEEPALIVE_INTERVAL_MS=15000
```

补充说明：

- 桌面端会读取程序同目录下的 `codexmanager.env`
- 但桌面端默认数据库不放在程序目录，而是放在系统应用数据目录
- 默认数据库位置可参考根说明里的“默认数据目录”： [../README.md](../README.md)

### Service 版

如果你用的是 `codexmanager-start` 一键启动包，更推荐把程序和 `env` 文件放成下面这样：

```text
codexmanager-service-bundle/
├─ codexmanager-start.exe
├─ codexmanager-service.exe
├─ codexmanager-web.exe
├─ codexmanager.env
└─ web/
   └─ ...
```

对应 `codexmanager.env` 示例：

```dotenv
CODEXMANAGER_SERVICE_ADDR=0.0.0.0:48760
CODEXMANAGER_WEB_ADDR=0.0.0.0:48761
CODEXMANAGER_DB_PATH=./data/codexmanager.db
CODEXMANAGER_RPC_TOKEN_FILE=./data/codexmanager.rpc-token
CODEXMANAGER_UPSTREAM_PROXY_URL=http://127.0.0.1:7890
```

这时目录通常会长成这样：

```text
codexmanager-service-bundle/
├─ codexmanager-start.exe
├─ codexmanager-service.exe
├─ codexmanager-web.exe
├─ codexmanager.env
├─ data/
│  ├─ codexmanager.db
│  └─ codexmanager.rpc-token
└─ web/
   └─ ...
```

补充说明：

- `CODEXMANAGER_DB_PATH=./data/codexmanager.db` 这种相对路径，会按“可执行文件所在目录”解析
- `CODEXMANAGER_RPC_TOKEN_FILE` 也是同样规则
- 如果你不写 `CODEXMANAGER_DB_PATH`，Service 版默认会把数据库放到程序目录下的 `codexmanager.db`

## 排障建议

### OpenAI 上游代理到底作用在哪

`CODEXMANAGER_UPSTREAM_PROXY_URL` / 设置页“OpenAI 上游代理”当前主要接管的是：

- 网关向上游平台发起的请求
- 启用 `CODEXMANAGER_USE_WEBSOCKET_UPSTREAM=1` 后的 ChatGPT 上游 WebSocket 请求
- 用量查询请求
- `refresh_token` 刷新 access token 的请求

安全提示：

- `auth.openai.com` / `oauth/token` 等登录态刷新链路必须走 OpenAI 支持的地区出口；不要把香港等受限节点纳入这条链路的自动轮换。
- 如果刷新请求返回 `unsupported_country_region_territory`，Service 会将账号标记为 `refresh_token_region_blocked` 并暂停后续自动刷新；修正代理后需要手动恢复账号。

默认不接管的是：

- 你本机浏览器 / 桌面端访问 `localhost` / `127.0.0.1` 的本地回环请求
- 本地 service 与 web 之间的回环通信
- 登录回调成功后的 OAuth `code -> token` 兑换链路

补充规则：

- 如果同时设置了 `CODEXMANAGER_UPSTREAM_PROXY_URL` 和 `CODEXMANAGER_PROXY_LIST`，单个上游代理优先，代理池会被旁路。
- `CODEXMANAGER_PROXY_LIST` 更适合“按账号稳定分流多个出口”；`CODEXMANAGER_UPSTREAM_PROXY_URL` 更适合“全局统一走一个出口”。
- `CODEXMANAGER_UPSTREAM_PROXY_BYPASS_HOSTS` / 设置页“代理 Bypass 域名”只影响聚合 API 上游地址；一行一个或用逗号/分号分隔，支持精确域名和 `*.example.com` 子域通配。命中后该聚合 API 直连，不使用 `CODEXMANAGER_UPSTREAM_PROXY_URL`。

### 改了 env 文件但没生效

优先检查：

1. 是否重启了对应进程
2. 是否已有同名系统环境变量
3. 是否又被设置页持久化配置覆盖

### 设置页改了但服务行为没变

优先检查：

1. 该配置是否属于“重启后生效”
2. 当前改的是专属设置卡片还是通用环境变量编辑器
3. service 日志里是否出现 reload / apply 失败

### 设置了网关传输参数但长流还是异常

优先检查：

1. `CODEXMANAGER_UPSTREAM_STREAM_TIMEOUT_MS` 是否过短，导致长时流式请求提前超时
2. `CODEXMANAGER_UPSTREAM_TOTAL_TIMEOUT_MS` 是否被设置成了非 `0` 的较短值，导致服务端按总时长截断
3. `CODEXMANAGER_SSE_KEEPALIVE_ENABLED` 是否已关闭，或 `CODEXMANAGER_SSE_KEEPALIVE_INTERVAL_MS` 是否过长，导致中间链路把 SSE 误判为空闲断开
4. 客户端本身是否还有自己的超时或代理空闲断开限制；请求日志里的 `120s/1.8s` 左侧是请求总耗时，右侧是首包耗时，不一定代表服务端总超时配置

### 高并发下 SQLite FD 过高

优先检查：

1. `CODEXMANAGER_STORAGE_MAX_CONNECTIONS` 是否被调得过大；默认 `32` 会对同一数据库路径施加总连接上限
2. `CODEXMANAGER_FRONT_PROXY_MAX_BLOCKING_THREADS` 是否高于存储连接上限；默认会跟随存储连接池上限并限制在 `32` 以内
3. `CODEXMANAGER_STORAGE_ACQUIRE_TIMEOUT_MS` 是否过短；连接池耗尽时，请求会等待空闲连接，超时后返回存储不可用错误
4. Linux Service 版仍建议设置合理的 `ulimit -n`，但不应再依赖无限增大 ulimit 来兜住 SQLite 连接峰值

### 本地回环请求异常

优先检查：

- 是否把系统代理错误地应用到了 `localhost/127.0.0.1`
- 地址是否被写成非预期大小写或非 loopback 主机名
