# 构建发布与脚本说明

## 本地开发

### 前端
```bash
pnpm -C apps install
pnpm -C apps run dev
pnpm -C apps run test
pnpm -C apps run test:ui
pnpm -C apps run build
```

### Rust
```bash
cargo test --workspace
cargo build -p codexmanager-service --release
cargo build -p codexmanager-web --release
cargo build -p codexmanager-start --release

# codexmanager-web 默认会将 apps/out 打进二进制；先构建前端即可
pnpm -C apps run build:desktop
cargo build -p codexmanager-web --release

# 本地一键构建并启动 service + web
./scripts/run-service-app.sh
```

## Tauri 打包

### Windows
```powershell
pwsh -NoLogo -NoProfile -File scripts/rebuild.ps1 -Bundle nsis -CleanDist -Portable
```

### Linux / macOS
```bash
./scripts/rebuild-linux.sh --bundles "appimage,deb" --clean-dist
./scripts/rebuild-macos.sh --bundles "dmg" --clean-dist
```

Linux 打包需要 `squashfs-tools`，会校验每个 AppImage 根目录的 `.DirIcon`，缺失时自动修复。界面语言默认选择“自动检测”，桌面端跟随系统语言，Web 端跟随浏览器语言；支持中文、英文、俄文和韩文，其他语言回退英文。可以在设置或顶部栏选择“自动检测”或固定语言，立即生效并持久化保存。

## GitHub Actions
当前统一发布入口为 `.github/workflows/release-all.yml`。推送 `v*` 标签会自动执行 `build-and-publish`；也可以通过 `workflow_dispatch` 手动选择 `build-and-publish`、`build-artifacts` 或 `publish-artifacts` 模式。

### `release-all.yml`
- 用途：一键发布 Desktop + Service 全平台产物
- 构建平台：`Windows`、`macOS（dmg）`、`Linux`
- 前端 `dist` 先单独构建一次，再被各平台打包 job 复用
- 五个平台的 Desktop 与 Service 分别并行构建，Service job 同时产出对应的 Web 包和 Linux x86_64 Docker 归档；Release 等待两类构建全部成功。
- Desktop 缓存使用 `apps/src-tauri` 工作区，Service 缓存使用根工作区，分别保存，避免不同依赖图相互清理缓存。
- 输入：
  - `mode`：默认 `build-and-publish`，可选 `build-and-publish|build-artifacts|publish-artifacts`
  - `tag`：必填
  - `ref`：默认 `main`
  - `prerelease`：默认 `auto`，可选 `auto|true|false`
- 行为：仅执行打包与发布，不再包含服务器侧测试门

### 跨版本缓存

推荐在推送已验证提交到 `main` 后，从 `main` 发起 workflow_dispatch，并将输入 `ref` 固定为提交 SHA：

```powershell
$releaseCommit = git rev-parse HEAD
gh workflow run release-all.yml --ref main -f mode=build-and-publish -f tag=v0.6.0 -f ref=$releaseCommit -f prerelease=false
```

无需再单独推送同版本标签；发布任务会在成功后创建标签和 Release。这样缓存写入默认分支，后续主分支发布和标签构建都能复用。仅推送版本标签生成的缓存受 GitHub ref 范围限制，其他版本标签无法直接复用。首次构建、Rust 工具链变化或缓存淘汰后仍可能需要冷构建。

## Release 产物清单

### Desktop
- Windows：`CodexManager_<version>_x64-setup.exe`、`CodexManager-portable.exe`
- macOS：`CodexManager_<version>_aarch64.dmg`、`CodexManager_<version>_x64.dmg`
- Linux：`CodexManager_<version>_amd64.AppImage`、`CodexManager_<version>_amd64.deb`、`CodexManager-linux-portable.zip`

### Service
- Windows：`CodexManager-service-windows-x86_64.zip`
- macOS：`CodexManager-service-macos-arm64.zip`、`CodexManager-service-macos-x64.zip`
- Linux：`CodexManager-service-linux-x86_64.zip`
- Linux（web 测试包）：`CodexManager-web-linux-x86_64.zip`

### 发布类型
- `prerelease=auto` 时，`tag` 包含 `-` 会发布为 pre-release。
- `prerelease=auto` 时，不包含 `-` 会发布为正式版。
- `prerelease=true|false` 时，会覆盖基于 tag 的自动判断。
- 重跑同一 `tag` 时，会按当前输入同步 Release 元数据。
- GitHub 仍会自动附带 `Source code (zip/tar.gz)`。

## `scripts/rebuild.ps1`
默认用于本地 Windows 打包；`-AllPlatforms` 模式会调用 GitHub workflow。

### 常用示例
```powershell
# 本地 Windows 构建
pwsh -NoLogo -NoProfile -File scripts/rebuild.ps1 -Bundle nsis -CleanDist -Portable

# 触发 release workflow（并下载工件）
pwsh -NoLogo -NoProfile -File scripts/rebuild.ps1 `
  -AllPlatforms `
  -GitRef main `
  -ReleaseTag v0.6.0 `
  -GithubToken <token>

# 强制发布为 pre-release
pwsh -NoLogo -NoProfile -File scripts/rebuild.ps1 `
  -AllPlatforms -GitRef main -ReleaseTag v0.6.0-beta.1 -GithubToken <token> -Prerelease true
```

### 主要参数
- `-Bundle nsis|msi`：默认 `nsis`
- `-NoBundle`：仅编译，不出安装包
- `-CleanDist`：构建前清理 `apps/out`
- `-Portable`：额外输出便携版
- `-PortableDir <path>`：便携版输出目录，默认 `portable/`
- `-AllPlatforms`：触发指定 release workflow
- `-GithubToken <token>`：GitHub token；不传时尝试 `GITHUB_TOKEN`/`GH_TOKEN`
- `-WorkflowFile <name>`：默认 `release-all.yml`
- `-GitRef <ref>`：workflow 构建 ref；默认当前分支或当前 tag
- `-ReleaseTag <tag>`：发布 tag；`-AllPlatforms` 时建议显式传入
- `-Prerelease <auto|true|false>`：默认 `auto`
- `-DownloadArtifacts <bool>`：默认 `true`
- `-ArtifactsDir <path>`：工件下载目录，默认 `artifacts/`
- `-PollIntervalSec <n>`：轮询间隔，默认 `10`
- `-TimeoutMin <n>`：超时分钟数，默认 `60`
- `-DryRun`：仅打印执行计划

## 版本同步

仓库当前没有 `scripts/bump-version.ps1`。发版前请按[发布与产物说明](发布与产物说明.md)中的检查清单，核对根 `Cargo.toml`、`apps/package.json`、`apps/src-tauri/Cargo.toml`、`apps/src-tauri/tauri.conf.json` 和两个 `Cargo.lock` 的版本。
