# Сравнение сценариев и обязанностей по публикации

## Таблица сравнения `.github/actions/` и `scripts/release/`

| Сценарий | GitHub Действие | Соответствующий сценарий/ответственность |
|---|---|---|
| Tauri Повтор сборки | `.github/actions/build-tauri-with-retry/action.yml` | Цикл повторов реализован внутри Action; локальные эквиваленты: `scripts/rebuild.ps1`, `scripts/rebuild-linux.sh`, `scripts/rebuild-macos.sh`. |
| Service Упаковка | `.github/actions/stage-service-package/action.yml` | Staging выполняется внутри Action; локальная сборка бинарников использует `scripts/release/build-service-binaries.ps1` / `.sh` и платформенные staging-сценарии в том же каталоге. |
| GitHub Релиз | `.github/actions/publish-github-release/action.yml` | Загрузка через `gh release` реализована внутри Action; отдельного локального сценария с таким именем нет. |
| Подготовка среды выпуска | `setup-release-env` | Сборка внутренней среды рабочего процесса, в настоящее время не существует полностью эквивалентного независимого скрипта верхнего уровня |
| Подготовка переднего плана | `prepare-frontend-dist` | Создайте/загрузите конечную точку внешнего интерфейса продукта в рамках рабочего процесса. В настоящее время отдельного сценария верхнего уровня не существует |

## Соглашение о границах

### `.github/actions/`

Ответственный за:

- Повторно используемые шаги в рабочем процессе
- Унифицировать ввод и вывод по всем заданиям.
- Инкапсуляция среды CI/Release

### `scripts/release/`

Ответственный за:

- Фактические действия по сборке, упаковке и публикации.
- Реализация сценария, вызываемая локально или рабочим процессом.
- Постарайтесь сделать его независимым исполняемым.

### `scripts/*.ps1|*.sh`

Ответственный за:

- Вход на верхний уровень для разработчиков
- Единая организация параметров
- Закройте подэтапы сложного выпуска.

## Текущий исторический инвентарь сценариев

### Все еще ценно

- `rebuild.ps1`
- `rebuild-linux.sh`
- `rebuild-macos.sh`
- `release/build-service-binaries.ps1` / `.sh`
- `release/pack-frontend-dist.sh`
- `release/publish-ghcr-images.sh`
- Платформенные staging-сценарии в `release/*`
- `ci/check-websocket-pins.sh`

Причина:

- Все еще фактически используется локальной разработкой, ссылками на выпуск или рабочими процессами.
- Не потерянные устаревшие файлы

### Actions с реализацией внутри и без отдельного скрипта

`build-tauri-with-retry`, `stage-service-package` и `publish-github-release` реализованы в `.github/actions/`; одноимённых файлов в `scripts/release/` нет.

### На данный момент не найдено скриптов, которые имеют «только одну точку использования и могут быть удалены напрямую»

Более подходящей стратегией на этом этапе является не удаление, а:

1. Используйте `README.md`, чтобы указать стратификацию поступления.
2. Отдельно опишите скрипты, специфичные для CI, и локальные записи.
3. Если на сценарий не ссылаются в нескольких версиях подряд, рассмотрите возможность его архивирования или объединения.

## Рекомендации по техническому обслуживанию

- При добавлении возможностей рабочего процесса отдавайте приоритет определению того, следует ли повторно использовать существующие действия.
- При добавлении нового сценария выпуска сначала решите, является ли он «записью верхнего уровня» или «подэтапом CI».
- Если скрипт не подходит для локального выполнения, в README он должен быть четко помечен как «Только CI».
